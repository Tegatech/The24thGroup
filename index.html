From proven Excel model to maintainable web application.

A staged delivery plan for turning BSP's existing costing, design and engineering model into a structured web application while preserving verified logic, improving the user experience where the move from Excel genuinely allows it, and keeping every significant change traceable.

Starting pointExisting BSP workbook, controlled repository and documented engineering rules.

Delivery approachBuild, deploy, test with BSP, refine, accept, then expand.

Commercial approachSmall delivery blocks with review points, not one premature whole-project fixed price.

01 / Current position

A strong foundation is already in place.

The existing repository already captures a substantial amount of product, engineering and migration thinking. The next step is to convert that controlled knowledge into a working application rather than restart the analysis from zero.

Already substantially defined

  • Project → Body of Water → Proposal / Revision model
  • Scope → Design → Costs → CSA / Audit / Equipment / Specification flow
  • Controlled Excel baseline and evidence handling
  • Module Library and candidate module families
  • Shared data ownership and semantic contracts
  • Master Data principles
  • Engineering knowledge / source-guidance architecture
  • Override, audit and historic-reproducibility rules
  • Global interaction and UI standards
  • Heating as first end-to-end reusable module candidate

Still to be built

  • Production database and application data model
  • Authentication, RBAC and team access
  • Working Project / Body of Water experience
  • Frontend application shell and estimator workspace
  • Backend/API integration layer
  • Reusable module-instance framework
  • Revision snapshots and issued-proposal freezing
  • Master Data administration
  • Production output / PDF generation
  • Integrated, tested end-to-end application flows
Core framing

This is not a simple Excel-to-browser conversion. The application should preserve verified engineering and commercial intent, separate rules from workbook cells, and make controlled improvements where a web product can be clearer, safer or easier to use.

02 / Delivery plan

Build once, prove it, then expand.

The delivery approach is designed to produce usable software early, prove the reusable architecture with real BSP modules, and then scale the wider workbook onto those established patterns.

Foundation

Covered by the initial £500 engagement.

  • Supabase data model and authentication
  • Projects, Bodies of Water and revision foundation
  • Master Data and audit structure
  • Application shell and navigation
  • Catalyst development deployment
  • Repository production structure

Reference implementation

Prove the full application route using a real, representative BSP module.

  • Heating as the preferred first candidate
  • Scope, Design and shared values
  • Engineering calculation and equipment
  • Costing, CSA and Audit
  • Specification and MEP outputs
  • Revision, traceability and acceptance

Reuse and rollout

Use further representative modules to prove reuse before broader migration.

  • Measured construction / shell pattern
  • Itemised equipment pattern
  • Finishes / tiling pattern
  • Refine common module framework
  • Migrate wider module library in blocks
  • Re-estimate from actual delivery evidence

04 / Identity + product direction

BSP should feel like engineering software, not a spreadsheet skin.

The application identity uses a geometric pool mark, a compact BSP wordmark and the Build Cost Plan lockup. The visual system is intentionally restrained so the brand is recognisable without competing with technical work.

04 / Product direction

A purpose-built estimator, not Excel in a browser.

The interface should feel like professional engineering software: efficient for experienced estimators, clear about calculated and overridden values, and organised around BSP's actual workflow rather than the physical layout of the workbook.

Hierarchy

Organise screens by engineering/business meaning rather than generic “Inputs” and “Outputs”.

Context

Keep the current Body of Water, module, revision and issue state visible without repeating labels everywhere.

Efficiency

Keyboard-first numeric entry, predictable TAB flow, fast replacement and compact help.

State clarity

Calculated, default, overridden, excluded, optional and frozen values must never look identical.

TegaDes · Direction A

Estimator workspace as a calm engineering cockpit.

One persistent workspace: project context on the left, engineering task in the centre, live commercial/state intelligence on the right. The interface changes density by task rather than forcing every module into identical cards.

05 / Commercial model

Commercial model: staged build blocks.

The project is best handled as a sequence of defined delivery blocks. This gives BSP a working output and review point at each stage, while allowing later estimates to use evidence from the modules already implemented.

£500

Initial engagement. Covers the platform foundation, application shell, database/auth foundation, repo structure, deployment setup and first usable screens.

Next build block: estimated £750 to £1,000First end-to-end reference implementation, centred on Heating and the reusable application behaviour needed to support it.
No per-slice charging modelReference slices are used to prove the architecture. The commercial unit is a delivery block, not an individual module or workbook header.
Re-estimate after evidenceOnce the first reference implementation is working, the next 2 to 3 structural patterns can be scoped from actual delivery effort.
Wider rolloutThe broader module library is then migrated in agreed blocks using the proven framework. Pricing is based on remaining complexity and delivery velocity, not an arbitrary count of workbook modules.
InfrastructureUse BSP-owned services and free tiers during development where appropriate. Paid infrastructure is introduced only when usage or production requirements justify it.
Current whole-project planning envelope£6k to £10k

Indicative total including the £500 already paid. This is a planning range, not a fixed quote, and assumes the project remains broadly within the currently understood BSP scope.

Why the total remains a range

The first complete reference implementation will show how much of the wider workbook genuinely reuses the common architecture and how much requires distinct engineering logic. That evidence will allow the remaining estimate to be narrowed rather than guessed.

  • Next firm block remains estimated at £750 to £1,000
  • Future blocks are priced against delivered evidence
  • Material new features or major changes to the agreed product or engineering model are scoped separately
  • AI-assisted implementation is reflected in the pricing, while architecture, verification, integration, acceptance and delivery responsibility remain part of the engagement

Technology stack

Recommended application stack.

The stack keeps engineering and commercial rules independent from the interface so the application remains testable, maintainable and adaptable as BSP grows.

Frontend

React + TypeScript

Estimator workspace, project navigation, forms, module screens, revision views and application interactions.

Backend / API

Python

Application services, orchestration, validation and controlled access to the engineering and commercial domain layer.

Engineering Engine

Python

All verified engineering calculations and business rules live here, independently of the UI. This is the core parity-tested layer used by Design, Costs, CSA, Audit, equipment and specification outputs.

Data

PostgreSQL via Supabase

Projects, Bodies of Water, revisions, module instances, master data, overrides, audit history and application state.

Authentication

Supabase Auth

User authentication and the foundation for BSP role and permission controls.

Hosting

Zoho Catalyst

Existing BSP Catalyst access is used for development, prototyping and testing where appropriate, with the free tier used while the application remains within suitable limits.

Source Control

GitHub

Controlled source of truth for code, tests, architecture decisions, evidence and technical documentation.

Testing

Python + TypeScript test suites

Unit tests, Excel parity tests, integration tests and end-to-end application tests remain separate and explicit.
