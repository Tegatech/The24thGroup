Software engineering starts before code and continues after release.

This placement deliberately uses products at different lifecycle stages. You will learn how teams discover problems, gather requirements, validate assumptions, build systems, test releases, accept work and operate software in real use.

01 · Programme idea

One placement. Almost the full lifecycle.

Each product has a different job in your learning. You are not expected to become an expert in every system. The goal is to understand why the work changes as a product matures.

02 · Product map

Five products. Five learning contexts.

The products below are not assignments of equal priority. Replay, Oroko and Koroko are the most likely hands-on testing surfaces. Igho provides build visibility. Ogoro is a later discovery and requirements exercise if time allows.

Ogoro

Discovery + requirements
Problem + solution

Businesses using grid power, generators, inverters or solar often lack a reliable view of usage, cost, outages and operating decisions. Ogoro explores how operational energy data can become useful intelligence.

What you learn

Requirements gathering, observation, business analysis, process analysis, product validation and how solution architecture begins before implementation.

Koroko

Validation
Problem + solution

Nigerian addresses can be inconsistent and difficult for software to search, standardise and trust. Koroko is building address infrastructure for search, resolution, standardisation and future verification.

What you learn

API validation, data quality, real-world assumptions, external dependencies, address terminology, regression testing and the difference between test data and authoritative data.

Igho

Active build
Problem + solution

Small teams and project-based organisations can run payroll through fragmented spreadsheets, bank details, approvals and manual payment records. Igho is being built as a controlled payroll system.

What you learn

How architecture becomes milestones, authentication and access control, data models, APIs, UI implementation, CI and why financial systems need strong correctness and auditability.

Oroko

Testing + acceptance
Problem + solution

Teams often understand processes informally but struggle to document, analyse and govern them consistently. Oroko provides structured process mapping, procedures, sharing and developer access.

What you learn

Product QA, acceptance testing, canvas behaviour, permissions, files, public sharing, API/MCP testing, bug reporting and re-testing fixes.

Live use
Problem + solution

Running a publication involves submissions, editorial work, publishing, distribution and partnerships across multiple systems. Replay connects those workflows so content can move through a more reliable operating process.

What you learn

Functional testing in live operational workflows, integrations between tools, real user behaviour, support issues and how production problems differ from development-only bugs.

04 · How we test

Understand. Test. Investigate. Record. Re-test.

Testing is the main practical thread of the placement. A useful tester does more than click buttons: they understand intent, reproduce behaviour and provide enough evidence for somebody else to act.

01

Understand

What problem or user need is this feature meant to solve?

02

Test

Follow the expected path, then try realistic edge cases.

03

Investigate

Use DevTools, API responses and available data to narrow the failure.

04

Record

Capture expected vs actual behaviour, steps, screenshots and environment.

05

Re-test

When fixed, confirm the original scenario and nearby flows still work.

A good bug report answers

  • What were you trying to do?
  • What should have happened?
  • What actually happened?
  • Can you reproduce it consistently?
  • Which environment, account or device was used?
  • Is there useful console/network evidence?

Think about the failure type

  • UI or usability problem
  • API or backend problem
  • Authentication or permission problem
  • Data quality or persistence problem
  • Integration problem between systems
  • Requirement is unclear rather than software being broken
05 · Later exercise · Ogoro

Learn how requirements are discovered.

Because you are in Nigeria and can observe a real shop/supermarket environment, Ogoro may become a later practical exercise in requirements gathering and solution analysis.

Do not start by suggesting features. Start by understanding how the business currently operates. Observe energy sources, generator use, fuel purchasing, outages, record keeping and the decisions the owner actually needs to make.

A useful chain is: real-world problem → current process → pain point → requirement → possible solution → validation → build → test.

How is generator fuel currently purchased and recorded?
Who knows when the generator ran and for how long?
What happens when grid power fails?
What information does the owner wish they had at the end of the week or month?
What decision would better information actually change?
Is the real issue cost, theft, maintenance, downtime, budgeting or something else?
06 · Placement progression

Structured exposure, not everything at once.

The programme should respond to what is actually ready to test. These phases are guidance rather than a rigid syllabus.

Weeks 1–2

Foundations

Set up core tools, understand the products, learn Git/GitHub basics, testing language, issue handling and how the Group works.

Weeks 3–5

Guided testing

Focus mainly on Replay and available Oroko/Koroko flows. Follow prepared test scenarios, report defects and re-test fixes.

Weeks 6–9

Small ownership

Take responsibility for a contained testing area, documentation improvement, QA task or small engineering change with review.

Weeks 10–12

Broader engineering

Observe Igho's build process, complete an Ogoro discovery exercise if appropriate, document learning, demo work and close the SIWES record.

07 · Evidence & logbook

Show what you learned, not just what you clicked.

Your weekly logbook should connect activities to software-engineering concepts. Screenshots, issue links, PRs, test evidence and short reflections can support the formal SIWES record.

Weak: “Tested Oroko.”

Better: “Tested Oroko's public sharing flow across Canvas only, Procedure only and combined modes. Logged a defect where the selected state did not persist after refresh and attached reproduction steps.”

Weak: “Worked on Ogoro.”

Better: “Observed how a supermarket records generator fuel purchases and documented the current process, pain points and questions that need validation before proposing a software requirement.”
