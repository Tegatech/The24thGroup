August 2026
Prepared: 23 August 2026Period reviewed: 1–23 AugustBasis: Asana + GitHub + Group operating decisions

The portfolio is becoming easier to operate because the products are becoming clearer about what evidence they still need.

Oroko is now exposing real usability gaps through internal testing, Ogoro has moved from concept into a tangible mockup and operating narrative, and the Group itself now has a portfolio site plus a reporting and repository standard. Koroko remains strategically important but its launch evidence is still incomplete.

01 / Executive summary

What mattered this month.

This is a month-to-date review. Completion claims are restricted to what is supported by repository or operating evidence.

Summary

  • Oroko moved into genuine internal use and testing. August commits addressed workflow, process-library and canvas behaviour; testing on 19–20 August then surfaced concrete product gaps around future-state parity, branch labels, attachments and public sharing.
  • Ogoro became tangible. The repository was created with a platform mockup, whitepaper and process maps, followed by an energy intelligence dashboard and reports mockup.
  • The 24th Group itself became more operational. The portfolio site was established and refined, Igho was added, the visual system was tightened, and Group thesis, roadmap, product register, operating rhythm, repo standard and monthly review templates were added.
  • Koroko remains in a readiness/evidence phase. Asana still records public Slate preview deployment and a set of cutover, authentication, payment, API and operational evidence gates. No August commit evidence was found on the default KorokoAPI branch during this review.
  • Evidence quality is uneven across the portfolio. TheReplayMAG and Igho do not yet have structured Asana/repository evidence in the sources reviewed, so their product health cannot be assessed as confidently as Oroko, Koroko and Ogoro.

Founder attention

  • Keep Oroko's active work deliberately narrow: internal testing findings should drive the next implementation cycle before commercial expansion.
  • Decide the immediate customer-discovery rhythm for Ogoro so the new mockups are tested against operational reality rather than expanded in isolation.
  • For Koroko, close the gap between deployed implementation and live evidence before treating beta readiness as complete.
  • Finish the repository/status standard across active products so September reporting requires less reconstruction.

03 / Product reviews

Evidence, learning and next gates.

Task-level detail stays in Asana. This layer records outcomes and what they mean.

Oroko

On track · internal testing / hardening
Built / completed
  • Initial Oroko build established.
  • Canvas fitting, connection deletion and deterministic edges improved.
  • App boot and process hydration issues addressed.
  • Process library hydration/defaults hardened.
  • Start and End nodes made freely movable.
  • Tier one and two workflow fixes completed.
Learned
  • Internal use is now valuable enough to expose product-level inconsistencies rather than just technical bugs.
  • Current and Future State must behave as one coherent system, with explicit copy semantics.
  • Decision branches need immediate visual feedback on canvas.
  • Attachments need guidance, progress and clear success/error states.
  • Public sharing needs a read-only canvas option, not only procedure output.
Blocked / dependent

No external blocker is evident. The main constraint is product hardening: internal findings need to be resolved before external testing, pricing and launch-readiness work can be treated as meaningful.

Next
  • Prioritise the internal-testing defects by impact.
  • Bring Future State to parity with Current State.
  • Fix branch-label persistence and upload feedback.
  • Implement read-only public canvas sharing.
  • Move into structured external testing only after the core flow feels coherent.

Koroko

Watch · readiness / evidence
Built / completed

Asana records a public Catalyst Slate preview, a continuing AppSail private/workspace runtime, deployed account-control and Checker changes, payment hardening and source/deployment traceability from the prior release cycle.

Learned

The remaining work is less about adding surface area and more about proving runtime behaviour: API contract parity, authentication boundaries, organisation isolation, payment settlement, monitoring and rollback.

Blocked / dependent
  • Slate Checker/auth routing still needs explicit API Gateway/AppSail handling.
  • Desktop/mobile smoke evidence remains open.
  • API Gateway tranche parity and cutover remain open.
  • Live settlement, invoice, auth and isolation evidence remain open.
  • NIPOST API/data request is an external dependency awaiting response.
Next
  • Close cutover gates before public-domain change.
  • Collect live evidence for auth, payments, API and rollback.
  • Follow up NIPOST response and assess fields, coverage, reuse rights, coordinates, limits and update frequency when received.

Ogoro

Watch · concept validation
Built / completed
  • Initial platform mockup.
  • Whitepaper.
  • Eight process maps.
  • Energy intelligence dashboard and reports mockup.
Learned

The product now has enough shape to test a sharper question: which generator, fuel, maintenance or facility signals actually cause operators to take action or save money?

Blocked / dependent

No structured Asana execution plan or customer-discovery evidence is recorded yet. The risk is building a visually convincing dashboard before proving the decision problem.

Next
  • Run customer discovery with real facilities/operations users.
  • Test the dashboard against real decision moments.
  • Define a software-first wedge before considering custom hardware.

Igho

Watch · pre-build
Built / completed

The product was added to the Group portfolio, with a defined visual identity direction and positioning around payroll infrastructure for projects, creative productions and small teams.

Learned

The stronger wedge is not broad HR. The useful starting point is trusted payroll execution: employee setup, payroll preparation, approval, transfers, payslips and records, with project/creative contexts as a differentiator.

Blocked / dependent

No dedicated repository or Asana execution evidence was available in this review. The canonical final logo asset is also still to be exported.

Next
  • Define the smallest internal payroll proof for The 24th Group.
  • Set up the product repository/status source.
  • Keep scope firmly away from broad HR-suite expansion.

TheReplayMAG

Watch · operating / evidence thin
Built / completed

No August product-level build evidence was available in the Asana/GitHub sources reviewed. The venture remains represented as the Group's culture business on the new portfolio site.

Learned

The reporting process needs a lightweight source of truth for operating businesses too, not only software products.
